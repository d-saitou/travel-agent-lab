# travel-agent-lab

旅行履歴を登録・参照し、履歴を基に今後の旅行プランを提案するAIエージェントアプリ。

## 1 概要

### 1.1 目的
- LLM・RAGを使用したAIエージェントの開発を実践する。
- アプリ開発における生成AIの各種サービスの活用方法を習得する。
- バイブコーディング（生成AIへの指示を中心とした開発）を実践する。
- モダンな技術スタック・開発環境に触れる。

### 1.2 主要機能
- アカウント登録・サインイン
- 旅行履歴の登録・参照
- 履歴情報を基にした、チャット形式での旅行プランの相談・提案

### 1.3 前提・スコープ外
- 前提：学習目的のプロジェクトであり、個人の開発環境（Windows・WSL 2）でのみ動作させる。
- 前提：利用者は開発者本人を想定する。ただし、複数ユーザーの利用を前提に設計する。
- 前提：本番運用を見据えた構成で構築する。
- スコープ外：本番環境へのデプロイ・外部公開、スマートフォン向けの最適化、多言語対応

### 1.4 基本方針
以下の方針で開発を進める。
- 成果物（ドキュメント・コード）は生成AIが主体となって作成し、開発者による修正は必要最小限とする。
- 実装は、作業の規模に応じて以下のいずれかで進める。
  - 対話：VS Code上で生成AIに指示しながら実装する。新規機能等の規模の大きい実装に用いる。
  - Issue起点：GitHub Issueを基に、生成AIがプルリクエスト作成まで自動で行う。小規模な修正に用いる。
- 成果物は生成AIと開発者が相互にレビューする。観点は以下のとおり。
  - 正確性：内容に誤りがないこと
  - 簡潔性：冗長・重複がないこと
  - 整合性：他の成果物と矛盾がないこと（設計ドキュメントと実装の一致等）
- 設計判断・成果物の採否は開発者が最終決定する。
- 生成AIへの指示・ルール（AGENTS.md、CLAUDE.md等）はリポジトリで管理し、運用を通じて改善する。
- APIキー等の機密情報はリポジトリに含めず、生成AIへの入力にも含めない。
- 開発環境は冪等に構築できる仕組みとし、再構築や環境変更時の再実行を容易にする。

## 4 開発フロー

### 4.1 ブランチ運用
[GitHub Flow](https://docs.github.com/ja/get-started/using-github/github-flow)に従い、`main`は常に動作する状態を保つ。

1. `main`から作業ブランチを作成する。ブランチ名は`<type>/<内容>`とする（例：`docs/update-readme`）。
2. 作業ブランチにコミットし、プルリクエストを作成する。
3. プルリクエスト上で1.4の観点でレビューする。
4. `main`にマージし、作業ブランチを削除する。

Issue起点（1.4参照）の場合は、手順1〜2を生成AIエージェントが自動で行い、開発者は手順3以降を行う。

### 4.2 コミットメッセージ
[Angularのコミット規約](https://github.com/angular/angular.js/blob/master/DEVELOPERS.md#type)に従い、`<type>: <subject>`の形式とする。
- type：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`
- subject：変更内容を日本語で簡潔に記述する。
- 関連するIssueがある場合は、本文に`#<Issue番号>`を記載する。
