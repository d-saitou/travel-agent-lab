# travel-agent-lab

旅行履歴を登録・参照し、履歴を基に今後の旅行プランを提案・登録するAIエージェントアプリ。

## 1 概要

### 1.1 目的
- LLM・RAGを使用したAIエージェントの開発を実践する。
- アプリ開発における生成AIの各種サービスの活用方法を習得する。
- 対話型開発（バイブコーディング）を実践する（要件定義、アーキテクチャ設計、開発環境構築）。
- 仕様駆動開発（SDD：Spec-Driven Development）を実践する（機能単位の設計・実装）。
- モダンな技術スタック・開発環境に触れる。

### 1.2 主要機能
- アカウント登録・サインイン・サインアウト・パスワード変更・アカウント削除
- 旅行履歴の登録・参照・編集・削除
- 旅行プランの相談・提案（チャット形式）
  - 履歴情報を基に旅行プランを提案し、ユーザーの要望に応じて修正を繰り返す。
  - ユーザーが承諾した旅行プランを登録する（Human-in-the-loop）。
- 会話履歴の参照・削除
- 旅行プランの参照・編集・削除、旅行履歴への移行

### 1.3 前提・スコープ外
- 前提：学習目的のプロジェクトであり、個人の開発環境（Windows・WSL 2）でのみ動作させる。
- 前提：利用者は開発者本人を想定する。ただし、複数ユーザーの利用を前提に設計する。
- 前提：本番運用を見据えた構成で構築する。
- スコープ外：本番環境へのデプロイ・外部公開、スマートフォン向けの最適化、多言語対応

### 1.4 基本方針
以下の方針で開発を進める。
- 成果物（ドキュメント・コード）は生成AIが主体となって作成し、開発者による修正は必要最小限とする。
- 作業は、内容・規模に応じて以下の開発フローのいずれかで進める。
  - 対話型開発：生成AIと対話しながら進める。\
    要件定義、アーキテクチャ設計、開発環境構築等の機能横断的な作業に用いる。
  - 仕様駆動開発：[GitHub Spec Kit](https://github.com/github/spec-kit)を使用し、Spec Kitの手順（4.1.2参照）に従って進める。\
    新規機能の追加等、規模の大きい機能単位の設計・実装に用いる。
  - Issue起点開発：GitHub Issueを基に、生成AIがプルリクエスト作成まで自動で行う。\
    小規模な修正に用いる。
- 成果物は生成AIと開発者が相互にレビューする。観点は以下のとおり。
  - 正確性：内容に誤りがないこと。
  - 簡潔性：冗長・重複がないこと。
  - 整合性：他の成果物と矛盾がないこと（設計ドキュメントと実装の一致等）。
- 設計判断・成果物の採否は開発者が最終決定する。
- 生成AIへの指示・ルール（AGENTS.md、CLAUDE.md等）はリポジトリで管理し、運用を通じて改善する。
- APIキー等の機密情報はリポジトリに含めず、生成AIへの入力にも含めない。
- 開発環境は冪等に構築できる仕組みとし、再構築や環境変更時の再実行を容易にする。

## 4 開発プロセス

### 4.1 開発フロー
各フローとも、ブランチ・プルリクエストの扱いは4.2に従う。

#### 4.1.1 対話型開発
1. 作業ブランチを作成する（例：`docs/update-readme`）。
2. 生成AIと対話しながら成果物を作成し、コミットする。
3. プルリクエストを作成し、レビュー後にマージする。

#### 4.1.2 仕様駆動開発
1. 作業ブランチを作成する（例：`feat/travel-history`）。
2. 仕様（`/speckit-specify`）：機能の要件・受け入れ基準を定義する。
3. 計画（`/speckit-plan`）：技術的な設計（データモデル、API等）を定義する。
4. タスク（`/speckit-tasks`）：計画を実装タスクに分解する。
5. 実装（`/speckit-implement`）：タスクに従って実装する。
6. プルリクエスト（`specs/`の成果物、コード）を作成し、レビュー後にマージする。

- 手順2〜5は、成果物を開発者が承認してから次の手順に進む。
- 必要に応じて以下を使用する。
  - 明確化（`/speckit-clarify`）：仕様の曖昧な点を解消する。手順2の後に使用する。
  - 整合性確認（`/speckit-analyze`）：仕様・計画・タスク間の整合性を確認する。手順4の後に使用する。

#### 4.1.3 Issue起点開発
1. 開発者がIssueを作成する。
2. 生成AIが作業ブランチ作成・実装・プルリクエスト作成を自動で行う。
3. 開発者がレビューし、マージする。

- 実行基盤（`.github/`）・ブランチ名は決定後に追記する。

### 4.2 ブランチ運用
[GitHub Flow](https://docs.github.com/ja/get-started/using-github/github-flow)に従い、`main`は常に動作する状態を保つ。

1. `main`から作業ブランチを作成する。ブランチ名は`<type>/<内容>`とする（例：`docs/update-readme`）。
2. 作業ブランチにコミットし、プルリクエストを作成する。
3. プルリクエスト上で1.4の観点でレビューする。
4. `main`にマージし、作業ブランチを削除する。

### 4.3 コミットメッセージ
[AngularJSコミット規約](https://github.com/angular/angular.js/blob/master/DEVELOPERS.md#type)に従い、`<type>: <subject>`の形式とする。
- type：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`
- subject：変更内容を日本語で簡潔に記述する。
- 関連するIssueがある場合は、本文に`#<Issue番号>`を記載する。
